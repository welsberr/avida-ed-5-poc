The demo is about an infrastructure portfolio

The question for the BEACON demo is how a coding assistant changes when it can work alongside a set of purpose-built repositories: ClaimWright, GroundRecall, doclift, Didactopus, CiteGeist, and SciSiteForge. Most are infrastructure: their value appears in fewer lost decisions, less repeated setup, better evidence trails, and fewer preventable errors across tasks, rather than in one visible feature.

In this Avida-ED 5 effort, Codex helped inspect and change code, respond to tests, and write documentation. The maintainer set the goals, repeatedly corrected the work against tutorial and classroom needs, reviewed behavior, and decided which limitations must remain visible. The repositories did not replace that judgment.

Localization is the clearest cross-repository case

The Spanish preview adapted a workflow developed through TalkOrigins work and documented in SciSiteForge: use a local language model, provide a small explicit terminology set, preserve the source structure, and record what produced the translation. In the Avida repository, scripts/localize_es_catalog.py calls a local OpenAI-compatible llama.cpp endpoint, masks placeholders, applies Avida-specific terminology and manual overrides, and can read a TalkOrigins translation compendium supplied to the script. The runtime uses stable message IDs; a separate generator produces the compiled catalog; the provenance script records source hashes and translation counts.

The catalog currently records 346 candidate entries: 189 local-model translations, 7 preserved glossary entries, and 150 Codex-assisted wording suggestions. Structural checks verify IDs, placeholders, and catalog provenance, and recent review corrected selector and tooltip behavior. The preview remains explicitly unreviewed: the catalog records zero human-reviewed entries, and visual layout checks and qualified Spanish/scientific terminology review remain open.

This division of work had a practical effect: translation could be generated locally and checked in a repeatable way without treating model output as approved copy. Local inference avoids sending these strings to a hosted translation model and avoids its per-token charges, while using local compute; no cost comparison was recorded. The workflow also made uncovered work visible. It does not establish translation accuracy or that every visible string fits on screen.

What GroundRecall did across context breaks

Several context compactions and resumptions occurred during the broader work. GroundRecall is intended to preserve reviewed decisions and provenance so a later session can recover durable context instead of relying only on a shrinking transcript. In this project, the effect is partial rather than proven: the current queries surfaced related TalkOrigins translation practice and orientation policy, but not a detailed Avida-ED 5 task record. Repository files and commit history remained the authoritative source for current code and status.

This is still useful evidence about the boundary: memory can restore why a workflow exists, while the repository shows what is currently implemented. Retrieval scope also matters. Release-capped lookup withheld private-scoped records; access had to be explicitly widened for the maintainer’s own local review. The report uses only the high-level finding, not private note content.

How ClaimWright changes the work

ClaimWright describes a mixed enforcement model: advisory guidance for private exploration, soft gates for expensive or durable actions, and hard gates for public-release hazards. If included in an assistant’s active instructions or a connected policy tool, those checks can shape behavior before and after an action. They ask what evidence supports a claim, whether an action is reversible, whether private material is involved, and what assumptions or risks remain.

That distinction matters here. ClaimWright’s ideas help structure this report’s evidence and disclosure, but this Avida repository has no ClaimWright runtime integration, and no executable publication gate ran before its Pages deployment. It would be inaccurate to say ClaimWright automatically blocked, approved, or governed the release. A useful next step is to connect a documented public-artifact review to the release workflow while keeping final publication authority with the human maintainer.

Human effort and uncertainty

No time log was kept, and Git records commits rather than design discussion, review, waiting, or experimentation. A cautious retrospective estimate for direct maintainer direction and review on this prototype is several focused sessions, roughly 5–15 hours, with low confidence. It excludes upstream Avida 5 development, earlier Avida-ED work, the substantial prior effort of creating and maintaining the six infrastructure repositories, unattended build time, and any time spent outside the recorded project history.

The effort was not just a single prompt followed by acceptance. The maintainer repeatedly made substantive choices about the experiment, UI relationship to v4, use of legacy colors and graphics, Spanish localization, chart behavior, and how to describe limitations. The assistant carried out many implementation and writing iterations; the human decided which problems mattered and whether the changes met the goal.

It is not a claim about what any other Codex session would necessarily do.

How to measure infrastructure value in the next demo

Infrastructure effects can be assessed by recording the work they change, not only by counting visible features. A compact evaluation can use the same bounded task with and without one component, keep the human review standard constant, and log elapsed active time, retries, corrections, and completion quality.

  • GroundRecall: after a simulated or real interruption, measure time to recover task state, missing decisions, repeated questions, and corrections required before safe continuation. Compare retrieval with the session summary and Git alone. This Avida case is a useful mixed result: method-level recovery, no exact task record.
  • ClaimWright: record which checks changed the plan or draft, which gates found a real issue, which were irrelevant, and the review time added. Separate checklist use from an executable policy gate; report both gate catches and false alarms.
  • SciSiteForge localization method: track source-string coverage, terminology consistency, placeholder/catalog errors caught, human edits per string, untranslated controls, visual overflows, and final reviewer acceptance. Compare these with a small manually translated sample under the same review criteria.
  • doclift: on legacy manuals or lesson materials, compare extraction fidelity, table/figure recovery, correction time, and successful downstream use against direct copy-and-paste.
  • Didactopus: measure whether structured practice changes independent explanation, recall, or transfer after tool use, rather than counting generated learning materials alone.
  • CiteGeist: measure citation-field correction rates, verified identifier coverage, relevant sources discovered, false leads, and human minutes per accepted citation against the current manual bibliography workflow.

These are proposed measures, not results from the current prototype. A fair comparison would preregister task boundaries and quality criteria, preserve human review, and avoid attributing every improvement to the named tool when the assistant, source corpus, or reviewer also changed.
